# راهنمای فارسی Architecture Decision Library

«رکورد تصمیم معماری» یا ADR یک انتخاب مشخص و علت آن را ثبت می‌کند. وقتی بخشی از کد، ابزار توسعه یا روش اجرا تغییر می‌کند، با مراجعه به ADR می‌توان فهمید چه گزینه‌هایی بررسی شدند، هزینهٔ انتخاب چه بود و برای راستی‌آزمایی باید چه چیزی را خواند یا اجرا کرد.

این کتابخانه از Markdown برای نوشتن رکوردها، Git برای نگهداری تاریخچه و Python برای بررسی قرارداد فایل‌ها استفاده می‌کند. الگوی آن برای همین کتابخانه نوشته شده و از ایدهٔ ثبت ساختاریافتهٔ تصمیم‌ها در MADR الهام می‌گیرد. [نمایهٔ تصمیم‌ها](adr/README.md) · [مرجع MADR](https://adr.github.io/madr/)

## ساختار کتابخانه

| مسیر | کارکرد |
| --- | --- |
| `docs/adr/NNNN-title.md` | یک تصمیم با شناسهٔ چهاررقمی، وضعیت و تاریخ |
| `docs/adr/TEMPLATE.md` | الگوی نوشتن رکورد تازه |
| `docs/adr/README.md` | نمایهٔ قابل پیمایش که از رکوردها ساخته می‌شود |
| `docs/evidence/` | یادداشت‌های شواهد همراه با ارجاع به کد، تست یا اجرای CI |
| `scripts/check_adrs.py` | بررسی رکوردها و مقایسه یا تولید نمایه |
| `tests/test_check_adrs.py` | آزمون‌های قرارداد با فایل‌های آزمایشی مستقل |

اعتبارسنج رکوردهای Markdown را با Python 3.13 و کتابخانهٔ استاندارد می‌خواند. یک پاس متن و فرادادهٔ هر رکورد را بررسی می‌کند. پس از خواندن مجموعه، ارجاع‌های جایگزینی بین تصمیم‌ها را بررسی می‌کند و جدول Markdown را به ترتیب شناسه می‌سازد. در حالت عادی، جدول ساخته‌شده با فایل ذخیره‌شده مقایسه می‌شود تا تغییر عنوان یا وضعیت بدون به‌روزرسانی نمایه آشکار شود. [قرارداد فایل‌ها و دستورها](SPEC.md)

## اجزای یک رکورد

رکورد با عنوان H1 و سطرهای `Status: ...` و `Date: YYYY-MM-DD` آغاز می‌شود. نام فایلی مانند `0007-review-database-boundaries.md` شناسهٔ یکتا و فاصله‌گذاری با خط تیره را نشان می‌دهد. تیترهای H2 زیر باید به همین ترتیب و هر کدام یک بار بیایند.

1. **Context** مسئله، محدودیت و محرک تصمیم را روشن می‌کند. برای نمونه توضیح دهید چرا زمان نگهداری یا سازگاری اهمیت دارد.
2. **Options** دست‌کم دو راه عملی را به‌صورت فهرست می‌آورد. هزینه‌ای را که دست‌کم یکی از گزینه‌ها ایجاد می‌کند بنویسید.
3. **Decision** گزینهٔ انتخاب‌شده و علت متناسب با همان زمینه را ثبت می‌کند.
4. **Trade-offs** سود، هزینه، محدودیت و شرایط بازنگری انتخاب را توضیح می‌دهد.
5. **Confirmation** می‌گوید کدام مشاهده یا نتیجهٔ آزمون نشان می‌دهد که اجرا با تصمیم منطبق است.
6. **Evidence** به فایل یادداشت شواهد در مخزن پیوند می‌دهد. یادداشت می‌تواند خواننده را به کامیت مشخص، مسیر تست و اجرای CI برساند.

برای یک معیار خوب بنویسید «اجرای برنامه روی ورودی نمونه باید کد خروج ثبت‌شده و متن مورد انتظار را تولید کند». سپس مسیر تست و نسخهٔ کدی را که این رفتار در آن بررسی شده ثبت کنید. جملهٔ «طراحی بهتر است» معیار مشاهده‌پذیری در اختیار بازبین نمی‌گذارد. [الگوی رکورد](adr/TEMPLATE.md)

## ایجاد، بازبینی و جایگزینی

- هنگام ایجاد رکورد از `Proposed` استفاده کنید. مسئله، گزینه‌ها و معیار تأیید را پیش از تغییر وضعیت بنویسید.
- هنگام بازبینی، مشخص کنید که شواهد به همان انتخاب مربوط‌اند. فایل کد، تست یا گزارش CI باید نتیجه‌ای را نشان دهد که در بخش تأیید وعده داده‌اید.
- پس از پذیرش تصمیم، وضعیت `Accepted` را ثبت کنید. بازبینی محتوای رکورد و پذیرش آن مسئولیت نگهدارنده است.
- هنگامی که تصمیم دیگری جای انتخاب قبلی را گرفت، رکورد قبلی را نگه دارید، وضعیتش را `Superseded` کنید و پس از تاریخ، سطر `Superseded by:` را با پیوند Markdown به فایل جانشین بنویسید. زنجیرهٔ جایگزینی باید به رکوردی با وضعیت `Accepted` برسد و حلقه نداشته باشد. شناسهٔ قبلی را برای اشاره به همان تصمیم نگه دارید.

وضعیت درج‌شده در نمایه مشخص می‌کند کدام انتخاب جاری است. نمونهٔ عملی، تصمیم خواندن یک‌بارهٔ فایل در ابزار CLI و تصمیم بعدی برای پردازش جریانی است. هر رکورد زمینهٔ زمان خودش را نگه می‌دارد. [تصمیم قبلی و سطر جایگزینی](adr/0002-workspace-search-validation.md) · [تصمیم پردازش جریانی](adr/0006-stream-search-and-stage-matches.md)

## اجرای اعتبارسنج و به‌روزرسانی نمایه

از ریشهٔ نسخهٔ دریافت‌شده، نسخهٔ Python را ببینید و اعتبارسنج را اجرا کنید. برای اجرای بررسی کتابخانه و آزمون‌ها، PowerShell نیز در دسترس باشد.

```powershell
python --version
python -X utf8 scripts/check_adrs.py
pwsh -NoProfile -File scripts/verify.ps1
```

برای تولید نمایه، ابتدا خروجی برنامه را در یک متغیر نگه دارید و تنها پس از کد خروج صفر آن را روی فایل مقصد بنویسید. به این ترتیب یک رکورد نادرست باعث بازنویسی نمایهٔ فعلی نمی‌شود.

```powershell
$index = & python -X utf8 scripts/check_adrs.py --print-index
if ($LASTEXITCODE -ne 0) { throw 'Decision records failed validation.' }
$index | Set-Content -LiteralPath docs/adr/README.md -Encoding utf8
python -X utf8 scripts/check_adrs.py
```

برای بررسی یک کپی مستقل از کتابخانه، به `--root` مسیر ریشهٔ کپی را بدهید. کد `0` یعنی بررسی موفق بوده، `1` به خطای فایل یا ناسازگاری رکورد و نمایه اشاره دارد و `2` برای استفادهٔ نادرست از آرگومان‌های فرمان است. در حالت `--print-index` متن Markdown روی خروجی استاندارد نوشته می‌شود و می‌توانید آن را قبل از ذخیره مرور کنید. ## تمرین مصنوعی و خطاهای قابل تکرار

فرض کنید برای یک سرویس آموزشی میان Monolith ماژولار و جداسازی سرویس‌ها انتخاب می‌کنید. در بخش `Context` شرط استقرار و مرز مسئولیت ماژول‌ها را ثبت کنید. در `Options` هزینهٔ هماهنگی انتشار و پیچیدگی ارتباط شبکه را مقایسه کنید. در `Confirmation` بنویسید آزمون وابستگی باید نبود import ممنوع میان ماژول‌ها را بررسی کند. در این تمرین، تا وقتی نتیجه‌ای واقعی برای آن آزمون ندارید، مثال را در محیط جداگانه و با وضعیت `Proposed` نگه دارید.

روی کپی آزمایشی خود می‌توانید یک خطا در هر نوبت بسازید. دو فایل با شناسهٔ یکسان خطای شناسه می‌دهند. تاریخ نامعتبر یا وضعیت `Draft` قرارداد فراداده را نقض می‌کند. تغییر عنوان بدون تولید دوبارهٔ نمایه، ناسازگاری نمایه را نشان می‌دهد. حذف فایل شواهد نیز باید در نتیجهٔ بررسی دیده شود. سپس همان تغییر را برگردانید و دستور بررسی را دوباره اجرا کنید. این مسیر همان نوع ورودی ساختگی را به کار می‌گیرد که آزمون‌های رگرسیون بدون وابستگی به داده یا سرویس واقعی استفاده می‌کنند. [آزمون‌های اعتبارسنج](../tests/test_check_adrs.py)

## نمونه‌های واقعی و حدود اعتبارسنجی

- یک تصمیم شرح می‌دهد چرا Cobra در ابزار خط فرمان Go به‌کار رفته و چگونه رفتار فرمان از دید پوسته آزموده شده است.
- دو تصمیم به اجرای CI قابل استفادهٔ دوباره می‌پردازند. یکی ورودی ثابت PowerShell برای پروژهٔ فراخواننده را ثبت می‌کند و دیگری دربارهٔ نسخهٔ ابزار Go و خروجی ساخت تصمیم می‌گیرد.
- تصمیم مربوط به خود کتابخانه توضیح می‌دهد چرا قرارداد محدود Markdown و تولید نمایه با کتابخانهٔ استاندارد Python انتخاب شده‌اند.

اعتبارسنج در متن ADR پیوندهای سادهٔ نسبی فایل را بررسی می‌کند. بررسی بخش هدف یک پیوند Markdown، مقصدهای HTTP و پیوندهای داخل خود یادداشت شواهد بر عهدهٔ بازبین است. بازبین همچنین باید تشخیص دهد که یادداشت شواهد واقعاً ادعا را پشتیبانی می‌کند. نتیجهٔ اجرای CI و محدودیت‌های آزمون در پروندهٔ شواهد ثبت می‌شود.
